# Daybook

Native iOS task manager (SwiftUI, iOS 17+) in the spirit of Things 3. README.md has the layout and
the status of each phase; supabase/README.md covers the sync backend.

## Where things go

- Rules and data live in `Packages/TaskCore` (TaskCore: pure logic; TaskStore: SQLite, sync,
  Supabase) and get unit tests there. The app (`App/`) only displays them and calls into them.
- `Daybook.xcodeproj` is generated by XcodeGen and git-ignored: change `project.yml`.
- Anything outside the app process (widget, share extension, intents when the app is closed) writes
  through `SQLiteStore.update { }`, never by opening the database another way. That keeps the write
  in one transaction and records it for sync.
- Supabase objects live in the `daybook` schema with explicit grants. The Supabase project is
  **shared with another of the user's apps**: users, email templates, redirect URLs and rate limits
  are project-wide, so flag any change to them instead of making it.

## Checking work

- `swift test --package-path Packages/TaskCore` for logic.
- `/run-daybook` (`.claude/skills/run-daybook/driver.sh`) to build, run and drive the app in the
  simulator, including widgets, notifications and the share sheet. Run `smoke` after app changes.
- `/verify-main` after a `git pull`, or for any commit range: risk scan plus all automated checks.
- When reporting, say plainly what wasn't tested (for example sign-in against a real Supabase
  project, Siri, or anything only a device can show).

## Conventions

- Commit when asked; ask before every push.
- Commit messages: a short subject in the imperative, then a body saying what changed and why.
- After a feature, update README.md's status section (Done / Next) in the same commit.
- Keep comments like the existing code: a doc comment on types and non-obvious functions, short
  "why" comments inline, no restating the code.
